# Issue Capture

Treat the Issue as a record of the user's current decisions, not as a plan that you must complete on the user's behalf.

## When creating or updating an Issue

- Record only intent, requirements, constraints, decisions, and changes that the user explicitly stated.
- Do not invent or derive additional requirements.
- Do not add acceptance criteria unless the user explicitly provided or requested them.
- Do not add considerations, risks, edge cases, implementation steps, or follow-up work merely because they seem relevant.
- Do not fill gaps just to make the Issue look complete.
- A one-line or incomplete Issue is valid if that accurately represents what the user has decided so far.
- You may organize, rephrase, and fit the user's content into the repository's Issue template, but do not introduce new substantive decisions.

When the user discovers something during the work and asks to add it, update the Issue with that new decision.

## When the user asks for advice

If the user explicitly asks what is missing, requests review, asks for alternatives, or asks for an explanation:

- Actively analyze the problem.
- Explain missing considerations, risks, alternatives, or possible completion conditions.
- Distinguish your suggestions from decisions already made by the user.
- Do not write those suggestions into the Issue as requirements until the user accepts them.

## Core rule

When the user is deciding, record.
When the user asks for help deciding, advise.
