# EC2 Manual Deploy Measurement

이 문서는 [EC2 Manual Deploy Runbook](ec2-manual-deploy.md)대로 새 EC2에 처음부터 수동 배포할 때 걸리는 시간과 불편한 지점을 기록한다. 측정 기준은 [Issue #69](https://github.com/J4EU/Store-Expiration-Tracker/issues/69)를 따른다.

## 측정 조건

- 범위: Runbook 2-1 Data EBS 준비부터 8단계 동작 확인까지
- 시작 상태: 기존 Data EBS를 삭제하고, 로컬의 `terraform.tfvars`와 `.terraform/`을 모두 지운 상태
- 환경: t3.micro, 새로 생성한 EC2와 Data EBS, Docker Compose v5.6.0, Docker Buildx v0.37.2
- 시간은 녹화를 보며 수동으로 잰 대략값이다. 오타나 막혀서 헤맨 시간도 포함한다.
- 각 단계의 시작 시각은 첫 명령을 복사한 시각이다. 필요한 단계는 명령 실행 시각도 메모에 적는다.
- 단계 사이의 빈 시간은 Runbook에서 다음 단계와 명령을 찾는 시간이다.

- 처음부터 배포하는 데 약 6분 반에서 10분이 걸린다. 시간 자체는 큰 문제가 아니었다.
- 기계가 처리하는 시간은 두 회차가 거의 같다. 패키지 설치가 대부분인 4-1 단계는 1:05와 1:04였고, 7단계에서 명령 실행부터 build 종료까지는 20초와 18초였다.
- 줄어든 3분 24초는 대부분 사람이 직접 하는 부분에서 나왔다. 그중 절반 가까이(1:38)가 2-2에서 줄었다. 1회차의 오타와 `data_volume_id` 누락이 2회차에는 없었다.
- 익숙해진 2회차에도 값을 옮기고 파일을 편집하는 수작업은 여전히 번거로웠다. 가장 큰 부담은 시간이 아니라 이 수작업이다.

## 불편한 지점

<!-- 측정하며 불편하거나 번거로웠던 점을 적는다. 후속 이슈 생성은 이 문서의 범위가 아니다. -->

번거로웠던 순서대로 적는다.

1. 2-2 EC2 생성 전에 공인 IP와 `data_volume_id`를 tfvars에 직접 입력해야 한다. 두 회차 모두 가장 번거로웠다. 실제 운영에서는 한 번 설정하면 바꿀 일이 거의 없겠지만, 이 불편을 감수할 이유는 없어 보인다. `data_volume_id` 수동 입력은 [Issue #48](https://github.com/J4EU/Store-Expiration-Tracker/issues/48)에서 다룬다.
2. 2-2의 `data_volume_id` 입력 항목이 Runbook에서 잘 보이지 않는다. `allowed_operator_cidrs` 설명과 `curl` 코드 블록 아래에 있어서, 1회차에는 IP만 입력하고 넘어갔다가 `apply`가 실행되지 않았다.
3. 6단계에서 env 파일을 직접 수정해야 한다. `openssl`로 secret을 만들고 붙여 넣는 왕복이 있다. 오래 걸리지는 않지만 두 회차 모두 번거로웠다.
