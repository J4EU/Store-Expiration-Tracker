# Issue #6 Review: 폐기 이력 저장 범위 재검토

## 문서 목적

이 문서는 GitHub Issue `#6`에서 제기한 `폐기 당시 소비기한 스냅샷 필요성`을 다시 검토한 결과를 정리한다.

현재 프로젝트에서 중요한 것은 폐기 이력을 얼마나 많이 남기느냐가 아니라, `어떤 데이터를 왜 남기는지`를 MVP 목적과 맞춰 고정하는 것이다.

## 관련 이슈

- GitHub Issue: `#6 폐기 이력 저장 범위 재검토: 폐기 당시 소비기한 스냅샷 필요성`

## 이슈가 열린 이유

기존 문서에서는 `discard_histories`에 아래 값만 저장하기로 정리되어 있었다.

- 언제 폐기되었는지
- 어떤 상품이 폐기되었는지
- 몇 개 폐기되었는지

이후 메인 리스트에서 `폐기처리일`을 어떻게 보여줄지 검토하는 과정에서 아래 의문이 생겼다.

- `폐기처리일`보다 `폐기 당시 소비기한`이 더 중요한 데이터 아닌가
- 폐기 이력을 나중에 분석하려면 `소비기한 스냅샷`도 남겨야 하는 것 아닌가

이 문서는 그 의문을 `분석 목적` 기준으로 다시 검토한 결과다.

## 이번 검토에서 다시 고정한 기준

### 1. 분석의 목적은 발주 판단 보조다

이 프로젝트에서 말하는 분석은 일반적인 BI나 판매 예측 기능이 아니다.

핵심 목적은 아래에 가깝다.

- 폐기 데이터를 근거로 발주 유지 여부를 다시 보게 만든다
- 반복적으로 남아서 폐기되는 상품을 식별한다
- 점주에게 `이 상품은 발주를 줄이거나 중단할지 검토할 필요가 있다`는 의견을 데이터로 말할 수 있게 한다

즉, 이 프로젝트의 분석은 `예측 시스템`보다 `반복 폐기 패턴을 보여주는 근거 시스템`에 가깝다.

### 2. 지금 궁금한 것은 운영 해석보다 반복 폐기 패턴이다

이번 검토에서 가장 중요하게 확인된 질문은 아래였다.

- `소비기한이 다 될 때까지 팔리지 않고 남는 상품이 실제로 있었는가`

이 질문은 아래 정보만으로도 상당 부분 답할 수 있다.

- 어떤 상품이 폐기되었는가
- 언제 폐기되었는가
- 몇 개 폐기되었는가

반면 아래 질문은 현재 MVP의 핵심 질문이 아니다.

- 당일 폐기였는가, 하루 늦었는가
- 운영 규칙이 정확히 지켜졌는가
- 불량 상품 때문에 폐기된 것인가

이런 질문은 `운영 해석`에는 의미가 있을 수 있지만, 현재 목표인 `발주 판단 보조`의 필수 조건은 아니다.

## 결론

### 1. `discard_histories`는 현재 구조를 유지한다

현재 MVP 기준에서 `discard_histories`는 아래 역할이면 충분하다.

- 판매되지 않고 남아 실제로 폐기된 상품의 누적 근거를 저장한다
- 기간별, 상품별 폐기 수량 집계의 기반이 된다

따라서 현재 테이블 구조는 유지 가능하다.

- `id`
- `product_id`
- `discarded_date`
- `quantity`

### 2. `expiration_date` 스냅샷 컬럼은 지금 추가하지 않는다

처음에는 `폐기 당시 소비기한`도 남겨야 할 것처럼 보였지만, 현재 분석 목적을 다시 좁혀보면 필수값은 아니다.

그 이유는 아래와 같다.

- 발주 판단 보조의 핵심은 `반복 폐기`와 `폐기 수량`이다
- `소비기한 스냅샷`은 주로 운영 해석에 더 가깝다
- 현재 MVP에서 알고 싶은 것은 `왜 그렇게 폐기했는가`보다 `계속 안 팔리고 남는가` 쪽이다

즉 `expiration_date` 스냅샷은 `있으면 좋은 데이터`일 수는 있지만, 지금의 핵심 문제를 풀기 위한 `필수 데이터`는 아니다.

### 3. 대신 날짜 기준 분석 조회는 나중에 신경 써야 한다

현재 구조는 발주 판단용 최소 데이터로는 충분하다.
다만 이후 분석 화면이 추가되면, `특정 상품 1개 조회`보다 아래 같은 조회가 더 자주 필요할 수 있다.

- 이번 달 전체 폐기 현황
- 최근 3개월 상품별 폐기 수량 비교
- 어떤 월에 어떤 상품이 반복적으로 폐기되었는지 조회

즉 컬럼 확장보다 먼저, `기간 기준 집계가 많은가`를 보고 인덱스 방향을 다시 검토할 가능성이 있다.
현재 구조로도 이런 조회는 기능적으로 가능하지만, 데이터가 쌓이면 `discarded_date` 기준 조회 성능을 따로 챙겨야 할 수 있다.

## 이 결정으로 가능한 분석 질문

현재 구조만으로도 아래 질문은 다룰 수 있다.

- 최근 1개월 동안 어떤 상품이 가장 많이 폐기되었는가
- 최근 3개월 동안 반복적으로 폐기된 상품은 무엇인가
- 어떤 월에 어떤 상품이 많이 폐기되었는가
- 폐기가 반복적으로 나오는데도 계속 발주되는 상품은 무엇인가

## 보류한 질문

아래 질문은 현재 MVP 바깥으로 둔다.

- 폐기 시점이 소비기한 당일이었는가
- 운영 규칙상 하루 먼저 폐기해야 하는 상품이 실제로 그렇게 처리되었는가
- 불량 상품 폐기와 판매 부진 폐기를 구분할 것인가

이 질문들이 실제로 중요해지면, 그때 `expiration_date` 스냅샷이나 추가 이벤트 속성을 다시 검토한다.
