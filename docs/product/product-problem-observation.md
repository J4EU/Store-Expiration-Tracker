# Product Problem Observation

이 문서는 현재 Product spec이 아니라, 이 제품이 출발하게 된 현장 업무와 기존 POS의 제약을 기록한다.

## 관찰한 업무 흐름

편의점 POS에는 소비기한을 등록하고 조회하는 기능이 있었지만, 현장에서는 사용 빈도가 낮았다. 소비기한 기간조회는 기본값이 `오늘-내일`이고, 사용자가 기간을 지정할 수 있어도 한 번에 최대 7일까지만 조회할 수 있었다.

등록은 상품 바코드 스캔 뒤 캘린더에서 소비기한을 터치하고, 사용 방법이 명확하지 않은 시간 항목과 등록 수량을 입력한 다음 `등록`을 누르는 방식이었다. 숫자로 날짜를 입력할 수 없었고, 마지막 `등록`을 누르기 전에 다른 날짜를 조회하면 앞에서 입력한 정보가 모두 사라졌다. 등록 과정이 중간에 끊기기 쉽고, 다시 입력해야 하는 부담이 있었다.

실제 업무 흐름은 대체로 `조회 → 품목 확인 → 폐기 → 재진입 → 삭제 또는 갱신 → 반복`이었다. 근무자는 오늘까지인 품목을 확인해 가져온 뒤 POS 메인 화면의 폐기 메뉴에서 처리하고, 다시 소비기한 등록 메뉴로 돌아와 방금 처리한 품목을 삭제했다. 다음 소비기한이 있으면 다시 등록하고, 없으면 기존 정보를 삭제했다.

## 문제로 이어진 제약

- 품목 목록은 날짜별로 정렬되지 않았다. 목록에는 있지만 실제 진열 상품의 소비기한이 달라진 경우에도 기존 등록 정보를 삭제한 뒤 다시 등록해야 했다.
- POS는 소비기한이 없는 상태를 별도로 관리하지 못했다. 다음 소비기한이 없는 상태에서 기존 정보를 삭제하면 날짜뿐 아니라, 그 상품이 다시 확인이 필요한 관리 대상이라는 사실도 함께 사라졌다.
- 그 결과 근무자는 이미 처리한 상품과 다시 확인할 상품을 기억에 의존하거나 진열대를 다시 전수 확인해야 했다.
- 실제 점검은 모든 상품의 모든 소비기한을 미리 등록하는 방식이 아니라, 보통 가장 임박한 소비기한을 확인하고 처리한 뒤 다음 대상을 다시 확인하는 방식으로 이뤄졌다.

이 관찰은 소비기한 정보가 사라질 때 상품별 관리 맥락까지 끊긴다는 제품 문제를 드러냈다. 현재 해결 방식과 운영 규칙은 [Product Overview](overview.md)와 [Operating Rules](operating-rules.md)에 둔다.
