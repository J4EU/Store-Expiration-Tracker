# Issue #10 Review: 폐기 수량 0 상황 처리 정책 정의

## 문서 목적

이 문서는 GitHub Issue `#10 폐기 수량 0 상황 처리 정책 정의: "확인했지만 폐기할 상품이 없었음" 흐름 분리`를 검토하고, 그 뒤 현재 프로젝트 논의에서 정리한 MVP 기준 결론을 반영한다.

Issue #10 원문은 아래를 열어 둔 문제정의 문서다.

- `quantity = 0`을 폐기 이벤트로 허용할지
- 별도 이벤트나 별도 액션으로 분리할지
- 버튼 라벨을 무엇으로 둘지

이 문서는 그 이슈를 검토한 뒤, 현재 프로젝트 문서에 반영할 결론을 명시하는 데 목적이 있다.

## 이슈가 열린 이유

현재 메인 대시보드에는 `폐기 완료` 버튼만 있다.

이 흐름은 아래 전제를 깔고 있다.

- 실제로 폐기할 상품이 남아 있다.
- 폐기 수량은 1개 이상이다.
- 폐기 이력을 저장한다.
- 처리 후 현재 소비기한을 종료하고 다음 확인 흐름으로 넘긴다.

하지만 실제 운영에서는 아래 상황이 충분히 가능하다.

- 소비기한을 확인하러 갔더니 해당 소비기한 상품이 이미 다 판매되었다.
- 따라서 폐기할 수량은 0이다.
- 그래도 현재 소비기한 정보는 더 이상 유효하지 않다.
- 다음 소비기한 확인 필요 상태로는 넘어가야 한다.

현재 구조에서는 이 사건을 자연스럽게 처리할 수 없다.

- 폐기 수량 입력 최소값이 1이다.
- API도 `quantity > 0`만 허용한다.
- `더 보기 -> 소비기한 수정`은 잘못 입력된 값을 고치는 보조 흐름이지, 소비기한 확인 후 메인 처리 흐름으로 설계된 것이 아니다.

## 이슈 원문에서 열어 둔 지점

Issue #10 원문은 방향을 강하게 제안하지만, 아래 항목은 아직 선택지 형태로 남겨 두고 있었다.

- `quantity = 0`을 폐기 이벤트로 허용할지
- `discard_histories`에 넣을지, 별도 이벤트로 분리할지
- UI 라벨을 `판매 완료`, `재고 없음 확인`, `폐기 없음 처리` 같은 후보 중 무엇으로 둘지

이번 문서에서는 이 선택지들 중 현재 repo 문서에 반영할 결론을 아래처럼 고정한다.

## 이번 검토에서 다시 고정한 기준

### 1. 현재 화면에는 서로 다른 운영 사건이 2개 있다

메인 처리 카드에서 사용자가 실제로 하고 싶은 일은 아래 둘 중 하나다.

- 남아 있는 재고를 실제로 폐기한다.
- 소비기한은 확인했지만 폐기할 재고는 없음을 반영한다.

이 둘은 결과적으로 `현재 소비기한 종료 -> 다음 소비기한 확인 필요`라는 상태 전이는 비슷할 수 있다.
하지만 저장해야 하는 이력의 의미는 다르다.

### 2. `discard_histories`는 실제 폐기 이력으로 유지하는 편이 낫다

현재 MVP에서 `discard_histories`는 아래 목적에 맞춰 설계돼 있다.

- 어떤 상품이 반복적으로 남아 폐기되는지 본다.
- 기간별 폐기 수량을 집계한다.
- 폐기 데이터를 바탕으로 발주 유지 여부를 다시 본다.

이 목적이라면 `quantity = 0`을 같은 테이블에 넣는 것은 의미를 흐릴 가능성이 크다.

- 실제 폐기와 `폐기할 재고 없음`이 같은 이벤트처럼 보일 수 있다.
- 이후 집계 쿼리에서 0건 필터링 규칙을 따로 의식해야 한다.
- 폐기 횟수와 폐기 수량의 의미가 함께 흔들릴 수 있다.

따라서 `discard_histories`는 계속 `실제 폐기된 수량 > 0`만 저장하는 편이 더 단순하고 안전하다.

### 3. 이번 문제의 핵심은 `상태 종료`와 `이력 의미`를 분리하는 것이다

이번 상황에서 필요한 것은 아래 2가지를 동시에 만족하는 정책이다.

- 현재 소비기한은 더 이상 유효하지 않으므로 종료되어야 한다.
- 하지만 실제 폐기 이력은 남기지 않아야 한다.

즉 `상태 전이`와 `폐기 이력 저장`을 항상 같은 사건으로 묶어두면 안 된다.

## 결론

### 1. `폐기 완료`와 `폐기 없음`을 분리한다

메인 처리 카드의 핵심 액션은 아래 2개로 나눈다.

- `폐기 완료`: 실제 폐기 수량이 있을 때 사용
- `폐기 없음`: 소비기한은 확인했지만 이미 판매되어 폐기할 수량이 없을 때 사용

Issue 원문은 버튼 라벨 후보를 열어 두었지만, 현재 논의 기준에서는 `폐기 완료`와 짝이 맞고 의미가 짧고 분명한 `폐기 없음`을 채택한다.

이 구분이 있어야 사용자는 우회 없이 현재 운영 상황을 표현할 수 있다.

### 2. 두 액션은 상태 전이는 같고, 저장 의미는 다르다

공통점:

- 둘 다 현재 소비기한은 종료된 것으로 본다.
- 둘 다 현재 소비기한을 그대로 방치하지 않고, 다음 상태를 결정한다.

차이점:

- `폐기 완료`는 `discard_histories`에 실제 폐기 수량을 저장한다.
- `폐기 완료`는 처리 직후 `expiration_date = NULL`로 전환하고 이후 `미확인` 흐름으로 보낸다.
- `폐기 없음`은 폐기 이력을 저장하지 않는다.
- `폐기 없음`은 다음 소비기한을 바로 입력할 가능성이 높으므로, 즉시 입력 팝업을 먼저 열고 `지금 입력`과 `나중에 확인`을 함께 제공하는 편이 낫다.
- `폐기 없음`에서 새 소비기한을 입력하면 바로 저장하고, 입력하지 않으면 그때 `expiration_date = NULL`로 전환해 `미확인` 흐름으로 보낸다.

### 3. `폐기 없음`은 별도 이력보다 즉시 후속 입력 유도가 더 중요하다

`폐기 없음`을 별도 이벤트 테이블로 남길 수도 있다.
하지만 현재 MVP 기준에서는 우선순위가 낮다.

지금 먼저 필요한 것은 아래다.

- 사용자가 현재 소비기한을 정상 종료할 수 있을 것
- 폐기 분석 데이터의 의미를 유지할 것
- 다음 소비기한 확인 흐름으로 자연스럽게 이어질 것
- 근무자가 이미 다음 상품을 보고 있을 가능성이 높은 타이밍을 살릴 것
- 지금 입력하지 못해도 어떤 상품이 다시 확인 대상인지 시스템에서 잃지 않을 것

따라서 현재 단계에서는 `폐기 없음`에 별도 이력을 추가하기보다, 다음 소비기한을 바로 입력할 수 있는 팝업을 우선 두는 편이 더 실용적이다.
다만 입력을 강제하지는 않고, 확인이 어려우면 기존 `미확인` 흐름으로 보낼 수 있어야 한다.
이때 강제하지 않아도 되는 이유는 상품 정보가 삭제되지 않고, `expiration_date = NULL` 상태도 정상 관리 상태로 남아 사용자가 나중에 다시 확인할 수 있기 때문이다.

## 이 결정으로 정리되는 규칙

- `폐기 완료`는 실제 폐기 이벤트다.
- `폐기 없음`은 현재 소비기한 종료 확인 이벤트다.
- `discard_histories`에는 `quantity > 0`인 실제 폐기만 저장한다.
- `폐기 완료`는 처리 후 `expiration_date = NULL`로 전환한다.
- `폐기 없음`은 다음 소비기한 입력 팝업을 먼저 열고, 새 값을 입력하면 바로 저장한다.
- `폐기 없음`에서 지금 입력하지 않으면 그때 `expiration_date = NULL`로 전환한다.
- `expiration_date = NULL`은 누락이 아니라 `미확인` 상태이므로, 지금 입력하지 않아도 해당 상품은 다시 확인 대상으로 남는다.
- `소비기한 수정`은 계속 보조 수정 흐름으로 남기고, 메인 처리 흐름의 대체 수단으로 보지 않는다.

## 다음 반영 후보

- `폐기 완료`와 `폐기 없음`의 후속 상태 입력 방식 차이를 상위 결정 문서에도 같은 표현으로 맞추기
- 프론트엔드 문서에 `폐기 없음` 팝업의 기본 액션과 보조 액션 의미를 더 구체화하기
- 백엔드 문서에 `POST /expiration-checks/no-discard`의 optional `expiration_date` 의미를 구현 단계에서 다시 고정하기
