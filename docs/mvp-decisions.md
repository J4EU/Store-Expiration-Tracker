# MVP Decisions

## 문서 목적

이 문서는 `Store-Expiration-Tracker` 설계 과정에서 확정된 핵심 결정을 정리한다.

목적은 아래와 같다.

1. 구현에 직접 영향을 주는 기준을 고정한다.
2. 이후 작업에서 같은 논의를 반복하지 않도록 한다.

## 1. 상품 보존 방식

### 논의한 후보

- 더 이상 관리하지 않는 상품은 삭제한다.
- 상품은 삭제하지 않고 상태로 관리한다.

### 최종 결정

- 상품은 삭제하지 않고 `active` / `archived` 상태로 관리한다.

### 이유

- 삭제하면 관리 대상이었다는 사실과 관련 기록이 함께 사라진다.
- 이후 재활성화와 폐기 데이터 분석이 가능해야 한다.

## 2. 아카이빙 기준과 복구 방식

### 논의한 후보

- 자동으로 아카이빙한다.
- 사용자가 수동으로 아카이빙한다.

### 최종 결정

- 사용자가 수동으로 아카이빙한다.
- 주요 기준은 `재고 0 + 한동안 발주 X` 같은 현장 판단이다.
- 아카이브 복구 시 기본값은 `products.status = active`, `expiration_date = NULL`로 둔다.
- 아카이빙 시 현재 소비기한 추적도 중단하므로 `expiration_date = NULL`로 비운다.

### 이유

- 점포 운영 기준은 시스템 규칙보다 현장 판단이 우선이다.
- 아카이빙은 더 이상 현재 소비기한을 추적하지 않는 상태 전환이다.
- 복구 시점에는 현재 소비기한이 확정되어 있지 않을 수 있다.

## 3. 상품 식별 방식

### 논의한 후보

- 상품명 기준으로 관리한다.
- 바코드 기준으로 관리한다.
- 바코드와 별도 내부 식별자를 함께 사용한다.

### 최종 결정

- 사용자 기준 식별은 `바코드`로 한다.
- DB 내부 연결은 `Primary Key ID`로 한다.
- MVP는 수기 입력으로 시작하고, 이후 바코드 스캐너 입력으로 확장한다.

### 이유

- 현장 입력 방식과 향후 스캐너 도입 계획에 맞다.
- 상태 테이블과 이력 테이블은 내부 ID로 연결하는 편이 안정적이다.
- 처음 등록 시 소비기한 없이 상품만 먼저 추가하더라도 바코드 기준 식별이 흔들리지 않는다.

## 4. 현재 소비기한 상태 구조

### 논의한 후보

- 상품 하나에 현재 상태 row를 여러 개 둔다.
- 상품 하나에 현재 상태 row를 하나만 둔다.

### 최종 결정

- 각 상품은 현재 소비기한 상태 row를 하나만 가진다.

### 이유

- 이 프로젝트는 모든 소비기한 이력을 저장하는 시스템이 아니라 현재 추적 상태를 유지하는 시스템이다.
- 소비기한 변경 시 기존 row를 수정하는 쪽이 MVP에 맞다.

## 5. 현재 소비기한 상태 표현 방식

### 논의한 후보

- `tracked`, `empty`, `expired`, `due_today`, `due_tomorrow`처럼 상태를 세분화한다.
- `tracked`, `empty`만 컬럼으로 저장하고, 날짜 기준 분류는 조회 로직에서 계산한다.
- `expiration_date`만 저장하고, `NULL / NOT NULL`과 날짜 비교로 상태를 해석한다.

### 최종 결정

- `expiration_states.state` 컬럼은 두지 않는다.
- `expiration_date IS NOT NULL`이면 현재 추적 중인 소비기한이 있는 상태로 본다.
- `expiration_date IS NULL`이면 다음 소비기한이 아직 없거나 확인되지 않은 상태로 본다.
- `expired`, `due_today`, `due_tomorrow` 같은 분류는 조회 시 계산한다.

### 이유

- 현재 MVP에서 `tracked`와 `empty`는 `expiration_date`의 `NOT NULL / NULL`과 의미가 같다.
- 별도 상태 컬럼을 두면 같은 의미를 중복 저장하게 된다.
- 아카이빙 여부는 이미 `products.status = active|archived`로 표현하므로, 소비기한 테이블에 별도 상태값을 추가할 이유가 없다.
- 미래에 날짜 유무만으로 설명되지 않는 업무 상태가 실제로 생기면 그때 별도 컬럼 도입을 다시 검토한다.

## 6. 폐기 처리 후 상태 전이

### 논의한 후보

- 폐기 기록만 남기고 다음 상태 입력은 선택 사항으로 둔다.
- 폐기 처리 시 반드시 다음 상태를 함께 결정한다.

### 최종 결정

- 폐기 처리 시 반드시 다음 상태를 함께 결정한다.
- 다음 값은 `새 소비기한 입력` 또는 `expiration_date = NULL` 적용 중 하나여야 한다.

### 이유

- 이 프로젝트의 핵심은 폐기 기록 자체보다 상태가 끊기지 않는 것이다.
- 다음 값을 강제하지 않으면 이전 소비기한 정보가 방치될 수 있다.

## 7. 메인 대시보드 조회 기준

### 논의한 후보

- 오늘까지인 상품만 조회한다.
- 오늘과 내일 상품만 조회한다.
- 이미 지난 상품을 포함해 `소비기한 <= 내일`인 상품을 모두 조회한다.

### 최종 결정

- 메인 대시보드 한 화면에서 `expiration_date <= tomorrow`인 활성 상품과 `expiration_date IS NULL`인 활성 상품을 함께 보여준다.
- 다만 두 집합은 같은 목록으로 섞지 않고, 화면 안에서 레이아웃 또는 섹션을 분리해 보여준다.
- 여러 탭으로 나누지 않고 한 화면에서 바로 오갈 수 있게 구성한다.

### 이유

- 점포 운영상 **일부 상품**은 소비기한 전날 폐기한다.
- 이미 소비기한이 지났지만 아직 갱신되지 않은 상품도 놓치지 않아야 한다.
- 현재 소비기한이 비어 있는 상품도 같은 작업 화면에서 바로 확인하고 후속 입력으로 이어질 수 있어야 한다.

## 8. 폐기 이력 저장 범위

### 논의한 후보

- `언제`, `어떤 상품이`, `어떤 소비기한으로`, `몇 개` 폐기되었는지 저장한다.
- `언제`, `어떤 상품이`, `몇 개` 폐기되었는지만 저장한다.
- `언제`, `어떤 상품이` 폐기되었는지만 저장한다.

### 최종 결정

- `언제`, `어떤 상품이`, `몇 개` 폐기되었는지를 저장한다.

### 이유

- 향후 분석에서는 폐기 횟수보다 폐기 수량이 더 중요한 지표다.
- 기존 소비기한 날짜까지 저장하는 것은 현재 판단 기준상 필요성이 낮다.

## 9. 분석 방향

### 논의한 후보

- 판매 데이터 분석까지 포함한다.
- 폐기 데이터를 기반으로 발주 판단을 보조하는 방향으로 간다.

### 최종 결정

- 폐기 데이터를 기반으로 발주 판단을 보조하는 방향으로 간다.

### 이유

- 이 프로젝트에서 중요한 것은 판매 성과보다 폐기 운영 데이터다.
- `최근 3개월 기준 상품별 폐기 수량` 같은 지표가 더 직접적인 판단 근거가 된다.

## 10. 화면 구조 우선순위

### 논의한 후보

- 여러 화면과 네비게이션 구조를 먼저 설계한다.
- 메인 대시보드를 중심으로 두고, 이후 보조 화면으로 확장한다.

### 최종 결정

- 메인 대시보드를 중심으로 두고, 이후 네비게이션 구조로 확장한다.

### 이유

- MVP의 핵심 작업은 하나의 운영 화면에서 끝나는 것이 좋다.
- 아카이빙 조회나 이력 조회는 이후 보조 화면으로 확장할 수 있다.
