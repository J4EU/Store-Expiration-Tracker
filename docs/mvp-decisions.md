# MVP Decisions

## 문서 목적

이 문서는 `Store-Expiration-Tracker` 설계 과정에서 확정된 핵심 결정을 정리한다.

목적은 아래와 같다.

1. 구현에 직접 영향을 주는 기준을 고정한다.
2. 이후 작업에서 같은 논의를 반복하지 않도록 한다.

## 0. MVP 방향 전환 배경

방향 전환 자체의 배경과 흐름은 [MVP 방향 전환](https://github.com/J4EU/Store-Expiration-Tracker/blob/main/docs/mvp-pivot.md) 문서에서 따로 정리한다.

이 문서에서는 그 방향 전환 이후 확정된 설계 결론만 다룬다.

## 1. 상품 보존 방식

### 논의한 후보

- 더 이상 관리하지 않는 상품은 삭제한다.
- 상품은 삭제하지 않고 상태로 관리한다.

### 최종 결정

- 상품은 삭제하지 않고 `active` / `archived` 상태로 관리한다.

### 이유

- 삭제하면 관리 대상이었다는 사실과 관련 기록이 함께 사라진다.
- 이후 재활성화와 폐기 데이터 분석이 가능해야 한다.

## 2. 아카이빙 기준과 복구 방식

### 논의한 후보

- 자동으로 아카이빙한다.
- 사용자가 수동으로 아카이빙한다.

### 최종 결정

- 사용자가 수동으로 아카이빙한다.
- 주요 기준은 `재고 0 + 한동안 발주 X` 같은 현장 판단이다.
- 아카이브 복구 시 기본값은 `products.status = active`, `expiration_date = NULL`로 둔다.
- 아카이빙 시 현재 소비기한 추적도 중단하므로 `expiration_date = NULL`로 비운다.

### 이유

- 점포 운영 기준은 시스템 규칙보다 현장 판단이 우선이다.
- 아카이빙은 더 이상 현재 소비기한을 추적하지 않는 상태 전환이다.
- 복구 시점에는 현재 소비기한이 확정되어 있지 않을 수 있다.

## 3. 상품 식별 방식

### 논의한 후보

- 상품명 기준으로 관리한다.
- 바코드 기준으로 관리한다.
- 바코드와 별도 내부 식별자를 함께 사용한다.

### 최종 결정

- 사용자 기준 식별은 `바코드`로 한다.
- DB 내부 연결은 `Primary Key ID`로 한다.
- MVP의 상품 등록은 바코드 스캐너 중심으로 설계한다.
- 현재 MVP의 등록 시작 동작은 `바코드 입력 후 기존 상품 조회`로 둔다.
- 로컬 중심 상품 등록 작업에서는 스캐너의 `스캔 + 엔터` 입력이 곧 조회 실행으로 이어져야 하므로, 자동 조회도 MVP에 포함한다.
- 다만 키보드 직접 입력도 가능해야 하므로, 조회 버튼은 fallback으로 함께 유지한다.

### 이유

- 현장 입력 방식과 현재 로컬 선등록 작업 방식에 맞다.
- 상태 테이블과 이력 테이블은 내부 ID로 연결하는 편이 안정적이다.
- 처음 등록 시 소비기한 없이 상품만 먼저 추가하더라도 바코드 기준 식별이 흔들리지 않는다.
- 현재 개발 흐름에서는 배포 전에 로컬에서 상품 등록을 절반 이상 진행하는 것이 목표이므로, 등록 속도와 반복 입력 부담도 MVP 검증 대상이다.
- 이 상황에서는 `상품 등록이 실제로 굴러가는가`가 곧 핵심 검증 항목이므로, 입력 장치 이벤트 처리도 별도 고도화가 아니라 기본 등록 흐름의 일부로 본다.

## 4. 현재 소비기한 상태 구조

### 논의한 후보

- 상품 하나에 현재 상태 row를 여러 개 둔다.
- 상품 하나에 현재 상태 row를 하나만 둔다.

### 최종 결정

- 각 상품은 현재 소비기한 상태 row를 하나만 가진다.

### 이유

- 이 프로젝트는 모든 소비기한 이력을 저장하는 시스템이 아니라 현재 추적 상태를 유지하는 시스템이다.
- 소비기한 변경 시 기존 row를 수정하는 쪽이 MVP에 맞다.

## 5. 현재 소비기한 상태 표현 방식

### 논의한 후보

- `tracked`, `empty`, `expired`, `due_today`, `due_tomorrow`처럼 상태를 세분화한다.
- `tracked`, `empty`만 컬럼으로 저장하고, 날짜 기준 분류는 조회 로직에서 계산한다.
- `expiration_date`만 저장하고, `NULL / NOT NULL`과 날짜 비교로 상태를 해석한다.

### 최종 결정

- `expiration_states.state` 컬럼은 두지 않는다.
- `expiration_date IS NOT NULL`이면 현재 추적 중인 소비기한이 있는 상태로 본다.
- `expiration_date IS NULL`이면 다음 소비기한이 아직 없거나 확인되지 않은 상태로 본다.
- `expired`, `due_today`, `due_tomorrow` 같은 분류는 조회 시 계산한다.

### 이유

- 현재 MVP에서 `tracked`와 `empty`는 `expiration_date`의 `NOT NULL / NULL`과 의미가 같다.
- 별도 상태 컬럼을 두면 같은 의미를 중복 저장하게 된다.
- 아카이빙 여부는 이미 `products.status = active|archived`로 표현하므로, 소비기한 테이블에 별도 상태값을 추가할 이유가 없다.
- 미래에 날짜 유무만으로 설명되지 않는 업무 상태가 실제로 생기면 그때 별도 컬럼 도입을 다시 검토한다.

## 6. 폐기 처리 후 상태 전이

### 논의한 후보

- 폐기 처리 후 항상 다음 소비기한 입력까지 한 번에 끝낸다.
- 폐기 이벤트 종류에 따라 후속 상태 입력 방식을 다르게 둔다.

### 최종 결정

- `폐기 완료`는 실제 폐기 이력을 저장한 뒤 현재 소비기한을 `expiration_date = NULL`로 전환한다.
- `폐기 없음`은 별도 팝업에서 다음 소비기한 즉시 입력을 우선 유도한다.
- `폐기 없음`에서 새 소비기한을 바로 입력하지 않으면 그때 `expiration_date = NULL`로 전환한다.

### 이유

- 이 프로젝트의 핵심은 폐기 기록 자체보다, 어떤 상품이 현재 확인됨/미확인 상태인지가 시스템에 계속 남아 있는 것이다.
- 다만 실제 운영에서는 `폐기 완료` 직후와 `폐기 없음` 직후의 다음 행동 타이밍이 다를 수 있다.
- `폐기 없음`은 다음 상품 소비기한을 바로 확인하고 있을 가능성이 더 높으므로, 즉시 입력을 먼저 유도하는 편이 자연스럽다.
- 그렇더라도 입력을 강제할 필요가 낮은 이유는 상품 정보가 DB에서 삭제되지 않고, `expiration_date = NULL` 상태도 `미확인`이라는 정상 관리 상태로 남기 때문이다.
- 따라서 사용자는 지금 입력을 미뤄도 이후 `미확인` 목록에서 해당 상품을 다시 확인할 수 있고, 관리 흐름도 끊기지 않는다.

## 7. 메인 대시보드 조회 기준

### 논의한 후보

- 기본 진입 필터를 `전체`로 둔다.
- 기본 진입 필터를 `오늘 처리`로 두고, 전체 조회는 별도 필터로 둔다.
- 날짜별 세부 필터를 여러 개 둔다.

### 최종 결정

- 메인 대시보드 한 화면에서 `expiration_date IS NOT NULL`인 활성 상품과 `expiration_date IS NULL`인 활성 상품을 함께 보여준다.
- 다만 두 집합은 같은 목록으로 섞지 않고, 화면 안에서 레이아웃 또는 섹션을 분리해 보여준다.
- 여러 탭으로 나누지 않고 한 화면에서 바로 오갈 수 있게 구성한다.
- 메인 처리 대상 필터는 `오늘 처리 / 전체` 2개로 단순화한다.
- 기본 진입 필터는 `오늘 처리`로 둔다.
- `오늘 처리`는 `지난 상품`과 `오늘 만료 상품`을 함께 묶어 보여준다.
- `오늘 처리`에는 `유제품`이면서 `내일 만료`인 상품도 포함한다.
- `전체`는 등록된 모든 소비기한 상품이 실제로 저장되어 있는지 함께 조회하는 용도도 포함한다.

### 이유

- 점포 운영상 **일부 상품**은 소비기한 전날 폐기한다.
- 이미 소비기한이 지났지만 아직 갱신되지 않은 상품도 놓치지 않아야 한다.
- 현재 소비기한이 비어 있는 상품도 같은 작업 화면에서 바로 확인하고 후속 입력으로 이어질 수 있어야 한다.
- 메인 화면은 먼저 오늘 우선 처리할 목록을 보여주고, 필요할 때 전체 저장 상태를 확인할 수 있어야 한다.
- 편의점 운영 규칙상 일부 상품은 하루 먼저 폐기하므로, 카테고리 최소 분류로 `유제품`을 둬야 한다.

## 8. 폐기 이력 저장 범위

### 논의한 후보

- `언제`, `어떤 상품이`, `어떤 소비기한으로`, `몇 개` 폐기되었는지 저장한다.
- `언제`, `어떤 상품이`, `몇 개` 폐기되었는지만 저장한다.
- `언제`, `어떤 상품이` 폐기되었는지만 저장한다.

### 최종 결정

- `언제`, `어떤 상품이`, `몇 개` 폐기되었는지를 저장한다.
- `폐기 없음`은 폐기 이력으로 저장하지 않는다.

### 이유

- 향후 분석에서는 폐기 횟수보다 폐기 수량이 더 중요한 지표다.
- 현재 분석의 핵심은 `어떤 상품이 반복적으로 남아 폐기되는가`를 보는 것이다.
- 폐기 데이터를 바탕으로 발주 유지 여부를 다시 보는 데에는 `언제`, `어떤 상품이`, `몇 개` 폐기되었는지가 우선이다.
- `폐기 당시 소비기한`은 있으면 더 많은 해석이 가능하지만, 현재 MVP 기준에서는 필수 데이터가 아니다.
- `확인했지만 폐기할 재고 없음`은 현재 소비기한 종료 사건이지, 실제 폐기 수량 사건은 아니다.

## 9. 분석 방향

### 논의한 후보

- 판매 데이터 분석까지 포함한다.
- 폐기 데이터를 기반으로 발주 판단을 보조하는 방향으로 간다.

### 최종 결정

- 폐기 데이터를 기반으로 발주 판단을 보조하는 방향으로 간다.

### 이유

- 이 프로젝트에서 중요한 것은 판매 성과보다 폐기 운영 데이터다.
- `최근 3개월 기준 상품별 폐기 수량` 같은 지표가 더 직접적인 판단 근거가 된다.

## 10. 메인 처리 대상 카드의 수정 액션 노출 방식

### 논의한 후보

- 메인 처리 대상 카드에 `소비기한 수정`을 직접 노출한다.
- 수정 계열 액션을 별도 페이지로 분리한다.
- 메인 처리 대상 카드에서는 핵심 처리 액션만 먼저 보여주고, 수정 계열은 `더 보기`로 묶는다.

### 최종 결정

- 메인 처리 대상 카드에서는 `폐기 반영` 흐름을 중심으로 둔다.
- 메인 처리 대상 카드의 핵심 액션은 `폐기 완료`와 `폐기 없음` 2개로 둔다.
- `소비기한 수정`, `상품명 수정`, `바코드 수정`, `카테고리 수정`은 메인 카드에서 직접 나열하지 않고 `더 보기` 안에 묶는다.
- 수정 계열 액션을 별도 페이지로 바로 분리하지는 않는다.
- `폐기 없음`은 별도 팝업에서 다음 소비기한 즉시 입력을 우선 유도하되, 입력을 강제하지는 않는다.

### 이유

- 메인 처리 대상 화면의 핵심 목적은 `폐기 처리 -> 상태 반영` 흐름을 빠르게 끝내는 것이다.
- 실제 운영에는 `실제 폐기`와 `폐기할 재고 없음`이 모두 존재하므로, 메인 처리 흐름 안에서 둘 다 바로 처리할 수 있어야 한다.
- `폐기 없음`은 사용 시점상 다음 상품 소비기한을 바로 확인하고 있을 가능성이 더 높으므로, 즉시 입력을 유도하는 편이 작업 흐름과 잘 맞는다.
- `소비기한 수정`이 메인 카드에 강하게 노출되면, 사용자가 `폐기 반영` 대신 소비기한만 수정하고 끝낼 가능성이 있다.
- 그렇게 되면 실제로는 폐기 이력이 저장되지 않은 채 현재 소비기한만 바뀌는 사용 흐름이 생길 수 있다.
- 따라서 수정 액션은 시각적으로 분리하되, 아직 별도 관리 페이지로 나눌 정도의 규모는 아니므로 `더 보기`가 현재 단계에 가장 맞다.

## 10. 화면 구조 우선순위

### 논의한 후보

- 여러 화면과 네비게이션 구조를 먼저 설계한다.
- 메인 대시보드를 중심으로 두고, 이후 보조 화면으로 확장한다.

### 최종 결정

- 메인 대시보드를 중심으로 두고, 이후 네비게이션 구조로 확장한다.

### 이유

- MVP의 핵심 작업은 하나의 운영 화면에서 끝나는 것이 좋다.
- 아카이빙 조회나 이력 조회는 이후 보조 화면으로 확장할 수 있다.
