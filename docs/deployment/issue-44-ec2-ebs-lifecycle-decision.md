# Issue #44 Decision: EC2 / EBS 수명주기

## 문서 목적

이 문서는 GitHub Issue `#44 EC2 SQLite 데이터 저장소 수명주기 결정 및 구현`에서 확정한 EC2와 EBS의 책임 및 수명 주기 기준을 남긴다.

이번 문서는 구현 완료나 운영 검증 결과를 기록하지 않는다.

## 전제

현재 로컬 Compose 경로에서는 `sqlite_data` Docker named volume을 백엔드의 `/app/data`에 마운트한다. 이 구성은 컨테이너 생명주기와 SQLite 데이터를 분리하지만, EC2 인스턴스 또는 Root EBS 수명주기 변화 뒤의 데이터 보존을 확인한 것은 아니다.

현재 Terraform의 EC2 Root EBS는 `delete_on_termination = true`다. 별도 Data EBS와 그 연결·복구 절차는 아직 구현하거나 검증하지 않았다.

## 결정

### 평시 운영은 EC2 start/stop을 사용한다

근무 종료를 `terraform destroy`와 동일시하지 않는다. 평시에는 EC2를 매일 재생성하지 않고, 서비스 종료 후 EC2를 stop한다. 다시 사용할 때는 EC2를 start한 뒤 서비스를 실행한다.

`destroy` 또는 terminate는 비용 절감을 위한 일상적인 종료가 아니라 자원의 수명 종료가 필요한 경우에 사용한다.

### Root EBS와 Data EBS를 분리한다

SQLite 서비스 데이터는 별도 Data EBS에 둔다.

| 구분     | 책임                                                |
| -------- | --------------------------------------------------- |
| Root EBS | OS, Docker, 애플리케이션 등 재구성 가능한 실행 환경 |
| Data EBS | SQLite 서비스 데이터                                |

분리의 목적은 단순히 SQLite 데이터를 보존하는 것이 아니라, 데이터를 저장하는 독립된 저장 경계를 두는 데 있다. 보안 사고뿐 아니라 OS 문제나 운영 실수처럼 EC2 자체를 교체해야 하는 상황에서 실행 환경과 서비스 데이터를 서로 다른 수명주기와 복구 단위로 관리한다. 이때 기존 Data EBS를 새 EC2에 다시 연결해 사용하는 방식으로 복구 경계를 두므로, 실행 환경을 재구축할 때 SQLite 데이터까지 같은 복구 단위에 묶지 않는다.

### Root EBS는 정상 폐기 시 함께 삭제한다

Root EBS에는 서비스의 핵심 영속 데이터를 저장하지 않는다. 따라서 정상적인 EC2 폐기에서는 `delete_on_termination = true`를 기본 정책으로 유지한다.

장애 또는 침해 사고에서는 기존 Root EBS에 로그, 마지막 실행 상태, 설정 변경, 원인 분석 또는 침해 흔적이 남아 있을 수 있다. 이 경우에는 폐기 전에 조사 목적의 보존 필요성을 판단하고, 필요하면 스냅샷 등의 방법으로 명시적으로 보존한 뒤 정리한다.

### Data EBS 분리와 백업·복구를 구분한다

Data EBS를 분리해도 EC2 침해, 운영자 실수, 애플리케이션 버그, OS·파일시스템 문제, 잘못된 배포 또는 인프라 장애로부터 데이터의 신뢰성이 자동으로 보장되지는 않는다.

- 영속성: 정상 종료나 재시작 뒤 현재 데이터를 유지하는 것이다.
- 복구: 장애나 문제가 발생한 뒤 서비스를 다시 정상적으로 운영 가능한 상태로 만드는 전체 과정이다.
- 복원: 백업이나 스냅샷 등을 이용해 데이터를 이전의 신뢰 가능한 상태로 되돌리는 행위다.

Data EBS 분리는 영속성과 실행 환경 분리를 위한 선택이다. 기존 Data EBS가 정상이라면 새 EC2에 다시 연결해 서비스를 재개하는 것도 복구에 포함된다. Data EBS의 데이터를 이전 상태로 되돌려야 한다면 복원은 복구 과정의 일부가 될 수 있다.

또한 향후 스냅샷을 사용하게 되면 SQLite 데이터만 독립적으로 백업·복원할 수 있는 경계를 만든다. 이 경우 SQLite 데이터의 백업·복원을 위해 Root EBS까지 함께 다룰 필요가 없다.

다만 이번 Issue에서는 스냅샷 또는 백업 전략과 복원 검증 방식을 결정하거나 구현하지 않는다. 이 구분은 새로운 후속 설계를 추가하기 위한 것이 아니라, 이미 선택한 Data EBS 분리의 이유와 가치를 명확히 남기기 위한 것이다.

## 수용하는 비용

Data EBS 분리에 따라 EBS 수명주기 관리, EC2 연결(attach), 파일시스템·마운트 관리, Docker의 SQLite 경로 연결, EC2 교체 뒤 재연결을 관리해야 한다. 향후 백업·복원을 도입한다면 그 대상과 절차도 별도로 관리해야 한다.

이 평시 관리 비용은 서비스 데이터와 실행 환경을 독립적으로 관리하고, EC2 교체 시 실행 환경을 복구하는 경계와 SQLite 데이터를 백업·복원하는 경계를 명확히 분리하는 가치를 위해 수용한다.
