# Issue #20 Review: 배포용 인증/세션 설정 정리

## 문서 목적

이 문서는 GitHub Issue `#20 배포용 인증/세션 설정 정리`를 현재 repo 기준으로 다시 정리한 결과를 담는다.

이번 이슈의 핵심은 인증 기능을 새로 늘리는 것이 아니다.
이미 로컬에서 검증한 접근 제어 1차 구현을, `배포 가능한 운영 기준`으로 설명 가능하게 만드는 것이 목적이다.

특히 아래 질문에 대한 현재 결론을 고정한다.

- 1차 배포에서 지금의 서명된 세션 쿠키 방식을 유지해도 되는가
- 배포 환경에서는 쿠키 보안 설정을 어떻게 가져가야 하는가
- 서버 저장 세션은 지금 바로 필요한가
- 현재 방식의 한계를 어떤 운영 전략으로 보완할 수 있는가

## 관련 이슈

- GitHub Issue: `#20 배포용 인증/세션 설정 정리`

## 현재 구현 상태

현재 repo에는 접근 제어 1차 구현이 이미 들어가 있다.

- 운영자 계정 기반 로그인
- `POST /auth/login`
- `POST /auth/logout`
- `GET /auth/session`
- `GET /health` 제외 운영 API 보호
- `4시간` 고정 만료
- 서명된 세션 쿠키 기반 인증

즉, 지금 다시 정리해야 하는 것은 `로그인 기능 유무`가 아니라 `이 방식을 배포 기준으로 어디까지 받아들일 것인가`다.

## 이슈가 열린 이유

현재 인증은 로컬 전제에서는 충분히 동작한다.
하지만 이 상태를 그대로 배포 기준이라고 말하기에는 아직 빠진 설명이 있다.

특히 아래 항목은 배포 전에 기준이 필요하다.

- 운영 배포에서 쿠키 `secure` 설정을 어떻게 둘지
- 배포 호스트 기준 쿠키 전송 조건을 어떻게 볼지
- 현재 서명된 세션 쿠키 방식을 계속 유지할지
- 서버 저장 세션 전환이 필요한 조건이 무엇인지
- 로그아웃, 만료, 강제 무효화를 어디까지 지원 대상으로 볼지

## 이번 검토에서 다시 고정한 기준

### 1. 1차 배포 구조는 단일 호스트 기준이다

현재 1차 배포 방향은 `EC2 + Docker Compose` 기반이다.
프론트엔드와 API를 분리 호스트로 둘 계획이 아니라, 같은 배포 단위 안에서 함께 서비스하는 방향으로 본다.

이 전제는 중요하다.

- 쿠키 전송 조건을 단순하게 가져갈 수 있다.
- CORS와 cross-site 쿠키 문제를 1차 범위에서 크게 키우지 않아도 된다.
- 인증 방식 선택을 `멀티 서비스 연동` 기준으로 볼 필요가 없다.

즉 이번 이슈는 `여러 호스트 간 인증 전달` 문제가 아니라, `단일 운영 도구를 안전하게 배포할 수 있는가`를 묻는 문제에 더 가깝다.

### 2. 현재 인증 목적은 복잡한 사용자 관리가 아니라 운영 API 보호다

이 서비스의 현재 범위는 아래와 같다.

- 단일 운영자
- 단일 점포
- 공개 회원가입 없음
- 권한 레벨 세분화 없음

따라서 지금 인증에서 정말 필요한 것은 아래 정도다.

- 로그인한 운영자인가
- 세션이 아직 만료되지 않았는가

즉 현재 단계의 인증은 일반적인 사용자 플랫폼의 계정 시스템보다, 운영 화면을 외부에 그대로 열어두지 않기 위한 접근 제어에 더 가깝다.

### 3. 그래서 1차 배포에서는 서명된 세션 쿠키 방식을 유지할 수 있다

현재 세션 토큰은 서버가 서명한 값 안에 아래 정보만 담는다.

- `sub`: 사용자명
- `exp`: 만료 시각

그리고 요청 시 아래만 검증한다.

- 토큰 서명이 서버 비밀값 기준으로 유효한가
- 만료 시각이 지나지 않았는가

현재 요구사항에서는 이 정도면 충분하다.

- 운영자는 사실상 1명이다.
- 세션에서 추가 권한 정보나 복잡한 상태를 들고 다닐 필요가 없다.
- 서버가 매 요청마다 별도 세션 저장소를 조회하지 않아도 된다.

즉 이번 결정은 `이 방식이 가장 강력해서`가 아니라, `현재 문제 크기에 비해 가장 단순하고 충분해서` 채택하는 것이다.

### 4. JWT를 지금 굳이 따로 도입할 이유는 크지 않다

JWT는 이름이 익숙하고 일반적인 선택처럼 보일 수 있다.
하지만 현재 repo에서 JWT를 도입한다고 해서 본질이 크게 달라지지는 않는다.

- 둘 다 서버 서명 기반 토큰이다.
- 둘 다 서버가 별도 세션 상태를 저장하지 않는 구조로 갈 수 있다.
- 둘 다 탈취 토큰의 개별 강제 무효화에는 약하다.

즉 현재 범위에서는 `JWT라서 더 낫다`고 보기 어렵다.
오히려 지금처럼 단일 서비스와 단일 운영자 중심 구조에서는 용어와 구현 복잡도만 커질 가능성이 있다.

### 5. 서버 저장 세션은 더 강력하지만, 지금 당장 운영 이득이 더 크다고 보긴 어렵다

서버 저장 세션은 분명 장점이 있다.

- 특정 세션만 즉시 강제 종료할 수 있다.
- 비밀번호 변경 시 기존 세션 전체 무효화 정책을 더 자연스럽게 가져갈 수 있다.
- 여러 디바이스 세션을 따로 관리하기 쉽다.

하지만 지금 단계에서는 아래 비용도 함께 생긴다.

- 세션 저장소를 따로 운영해야 한다.
- 만료 정리 정책을 가져가야 한다.
- 세션 생성, 조회, 삭제 흐름을 서버 상태와 함께 관리해야 한다.

현재 서비스 범위에서는 이 비용이 아직 더 크게 느껴진다.
따라서 서버 저장 세션은 `지금 당장 필요하다`보다, `언제 필요해지는가를 문서화한다` 쪽이 더 맞다.

## 결론

### 1. 1차 배포에서는 현재 서명된 세션 쿠키 방식을 유지한다

현재 서비스 범위와 배포 구조를 보면, 1차 배포에서 signed session cookie를 유지하는 것이 가능하다.

그 이유는 아래와 같다.

- 인증 대상이 단일 운영자다.
- 세션에서 검증해야 할 정보가 단순하다.
- 프론트와 API를 분리 호스트로 다루지 않는다.
- 지금은 운영 API 보호가 우선이지, 복잡한 계정/세션 관리가 우선이 아니다.

### 2. 배포 환경의 쿠키 기본 기준은 `HttpOnly + Secure + SameSite=Lax`로 둔다

운영 배포에서는 HTTPS 전제를 둔 뒤, 인증 쿠키를 아래 기준으로 본다.

- `HttpOnly`: 프론트엔드 자바스크립트가 쿠키 값을 직접 읽지 못하게 한다.
- `Secure`: HTTPS 연결에서만 쿠키를 전송한다.
- `SameSite=Lax`: 일반적인 same-origin 중심 흐름을 유지하면서 불필요한 cross-site 전송을 줄인다.

현재 1차 배포 구조에서는 이 기준이 가장 자연스럽다.

### 3. 쿠키 `domain`은 우선 host-only 기준으로 둔다

1차 배포에서는 프론트와 API가 같은 배포 단위 안에 있으므로, 쿠키 `domain`을 억지로 넓게 주입할 이유가 크지 않다.

오히려 초기에는 host-only 쿠키로 두는 편이 더 단순하다.

- 필요 이상으로 쿠키 범위를 넓히지 않는다.
- 배포 호스트 기준 동작을 예측하기 쉽다.
- 추후 서브도메인 분리 필요가 생기면 그때 다시 검토할 수 있다.

### 4. 세션 정책은 `4시간 고정 만료`를 유지한다

현재 기준에서는 아래 정책을 유지한다.

- 로그인 시점부터 최대 `4시간` 유효
- 브라우저 종료는 부가 종료 조건으로 볼 수 있음
- 무활동 시간 기준 자동 로그아웃은 1차에서 보류

즉 현재 세션 정책은 `짧은 운영 창`을 전제로 한 단순한 고정 만료 정책으로 설명할 수 있다.

## 현재 방식의 한계

### 1. 개별 세션 강제 무효화는 어렵다

현재 방식은 서버가 세션 목록을 저장하지 않는다.
따라서 특정 세션 하나를 골라 즉시 끊는 기능은 자연스럽게 제공되지 않는다.

### 2. 탈취된 세션 쿠키는 만료 전까지 위험이 남을 수 있다

토큰이 유출되면, 서버는 그 토큰이 원래 브라우저에서 온 것인지 구분하기 어렵다.
따라서 만료 전까지는 악용 가능성이 남을 수 있다.

### 3. 비밀번호가 뚫리면 공격자는 새 세션을 다시 만들 수 있다

브루트포스나 자격 증명 유출로 비밀번호 자체가 노출되면, 세션 하나를 끊는 문제보다 더 큰 문제가 된다.
이 경우 공격자는 로그인으로 새 세션을 다시 만들 수 있기 때문이다.

즉 이 방식의 위험은 `세션 관리 한계`와 `로그인 보호 필요성`을 함께 봐야 한다.

## 운영 전략으로 보완할 수 있는 범위

현재 서비스 규모에서는, 위 한계를 당장 서버 저장 세션 도입으로 해결하기보다 운영 전략으로 일부 완화하는 접근이 가능하다.

### 1. 예방

- 강한 `ADMIN_PASSWORD` 사용
- HTTPS 전제와 `Secure` 쿠키 적용
- 로그인 시도 횟수 제한 같은 rate limiting 검토

### 2. 탐지

- 낯선 IP나 비정상 시간대 로그인 같은 이상 징후 감지 검토
- 이상 로그인 또는 반복 실패 시도 알림 검토

### 3. 대응

- 사고 대응 시 `SESSION_SECRET` 교체를 통한 기존 서명 세션 전체 무효화
- 필요 시 EC2를 일시 중지해 추가 피해 확산 차단

이 전략은 `서버 저장 세션과 동등한 통제력`을 제공하지는 않는다.
다만 현재 단일 운영자, 단일 점포, 단일 호스트 구조에서는 signed cookie의 한계를 운영 절차로 감당 가능한 범위에 두는 현실적인 접근이 될 수 있다.

## 서버 저장 세션 전환이 필요해지는 조건

아래 조건이 중요해지면 서버 저장 세션 전환 필요성이 커진다.

- 특정 세션만 즉시 강제 로그아웃해야 한다
- 비밀번호 변경 시 기존 세션을 더 정교하게 정리해야 한다
- 여러 운영자 계정과 권한 레벨을 지원해야 한다
- 여러 디바이스 세션을 구분 관리해야 한다
- 로그인 이상 징후 대응을 서버 상태와 더 강하게 묶어야 한다

즉 서버 저장 세션은 `현재 방식이 틀렸기 때문`이 아니라, `운영 요구가 더 커질 때 자연스럽게 넘어갈 다음 단계`로 보는 편이 맞다.

## 이번 결정으로 정리되는 규칙

- 1차 배포 구조는 `EC2 + Docker Compose` 기반 단일 호스트를 전제로 둔다.
- 1차 배포에서는 현재 signed session cookie 방식을 유지한다.
- 운영 배포의 쿠키 기본 기준은 `HttpOnly + Secure + SameSite=Lax`로 둔다.
- 쿠키 `domain`은 우선 host-only 기준으로 둔다.
- 세션은 로그인 시점부터 `4시간` 고정 만료를 유지한다.
- 개별 세션 강제 무효화는 현재 방식의 한계로 인정한다.
- 사고 대응 시 `SESSION_SECRET` 교체를 통해 기존 세션 전체를 무효화할 수 있다.
- 서버 저장 세션은 후속 운영 요구가 커질 때 다시 검토한다.

## 다음 반영 후보

- 배포 환경에서 쿠키 `secure` 여부를 환경 설정으로 분리하기
- 운영 배포 호스트 기준 CORS / origin 설정 방식을 구현과 문서에 함께 정리하기
- 로그인 시도 제한이나 이상 로그인 감지 같은 운영 보완책을 후속 이슈로 분리하기
- `SESSION_SECRET` 교체 절차를 운영 문서 또는 배포 문서에 별도로 정리하기
