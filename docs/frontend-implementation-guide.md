# Frontend Implementation Guide

## 문서 목적

이 문서는 Vue 기반 프론트엔드 1차 구현 범위를 고정한다.

목적은 아래와 같다.

1. 로컬 검증 단계에서 어떤 화면과 상호작용을 먼저 만들지 정한다.
2. 백엔드 API와 프론트 UI의 연결 기준을 맞춘다.
3. 구현 도중 범위가 불필요하게 커지는 것을 막는다.

## 1. 현재 전제

- 1차 사용자는 사실상 `1명(본인)`이다.
- 1차 목표는 `로컬에서 실제 운영 흐름을 검증하는 것`이다.
- 프론트엔드는 임시 정적 파일이 아니라 `Vue`로 구현한다.
- MVP의 핵심 중 핵심은 `한 번 등록한 상품이 시스템에서 사라지지 않는 것`이다.

## 2. 1차 화면 구조

### 좌측 사이드바: 소비기한 등록 진입

좌측 사이드바에는 `소비기한 등록` 진입 영역을 둔다.

기본 흐름:

1. 사용자가 `소비기한 등록` 액션을 누른다.
2. 등록 팝업이 열린다.
3. 팝업에서 먼저 `바코드`를 입력한다.
4. 사용자가 `조회`를 누르거나, 스캐너의 `스캔 + 엔터` 입력으로 자동 조회를 실행한다.
5. 이후 소비기한 등록 또는 신규 상품 등록이 이어진다.
6. 로컬 선등록처럼 반복 작업이 필요한 경우에는, 저장 후 등록 팝업을 닫지 않고 다시 `바코드` 입력 대기 상태로 돌아갈 수 있어야 한다.

필수 입력:

- `barcode`

선택 입력:

- `expiration_date`
- `category`

조건부 입력:

- `name`

규칙:

1. 상품 등록의 시작점은 `상품명 입력`이 아니라 `바코드 입력`이다.
2. 바코드가 기존 상품과 매칭되면, 기존 상품 정보를 보여주고 바로 소비기한 등록 또는 갱신으로 이어진다.
3. 바코드가 없을 때만 신규 상품 등록 흐름으로 넘어간다.
4. 신규 상품 등록이 필요한 경우에만 `name` 입력을 받는다.
5. 카테고리는 1차에서 `유제품` 또는 `미선택`만 받는다.
6. 중복 등록 시에는 단순 실패가 아니라 `이미 등록된 상품 정보`를 함께 안내한다.
7. 로컬 중심 등록 작업에서는 `바코드 스캔 + 엔터` 입력이 반복될 가능성이 높으므로, 바코드 스캐너 중심 등록 흐름을 1차 범위에 포함한다.
8. 다만 키보드 직접 입력도 계속 가능해야 하므로, 조회 버튼도 함께 유지한다.

### 메인 영역: 처리 대상

메인 영역은 오늘 우선 처리할 상품을 먼저 확인하고, 필요할 때 전체 저장 상태를 함께 조회하는 기본 작업 공간이다.

포함 대상:

- 지난 상품
- 오늘 만료 상품
- 내일 만료 상품
- 그 이후 소비기한 상품

표시 방식:

- 한 화면 안에서 필터를 전환할 수 있어야 한다.
- 필터는 `오늘 처리 / 전체` 2개를 둔다.
- 기본 진입 필터는 `오늘 처리`로 둔다.
- `오늘 처리`에는 `지난 상품`과 `오늘 만료 상품`을 함께 포함한다.
- `오늘 처리`에는 `유제품`이면서 `내일 만료`인 상품도 함께 포함한다.
- `전체`에서는 등록된 모든 소비기한 상품을 소비기한 기준 시간순으로 정렬한다.

처리 대상 카드에서 가능한 행동:

- 폐기 완료
- 폐기 없음
- 아카이브
- 더 보기

`더 보기`에 포함할 수정 계열 액션:

- 소비기한 수정
- 상품명 수정
- 바코드 수정
- 카테고리 수정

폐기 처리 UX 규칙:

1. 메인 카드의 핵심 처리 액션은 `폐기 완료`와 `폐기 없음` 2개다.
2. `폐기 완료`의 입력값은 `수량`이며, 실제 폐기 수량이 있을 때만 사용한다.
3. `폐기 없음`은 소비기한은 확인했지만 이미 판매되어 폐기할 수량이 없을 때 사용한다.
4. `폐기처리일`은 입력값이 아니라 `폐기 완료` 시점 기준으로 시스템이 기록한다.
5. `폐기 완료` 시에는 폐기 이력을 저장한 뒤 현재 소비기한을 `NULL`로 전환한다.
6. `폐기 없음` 클릭 시에는 다음 소비기한을 바로 입력할 수 있는 팝업을 먼저 연다.
7. 팝업의 기본 흐름은 `다음 소비기한 입력`이며, 보조 선택지로 `나중에 확인`을 둔다.
8. `폐기 없음` 팝업에서 새 소비기한을 입력하면 바로 저장하고, 입력하지 않으면 그때 현재 소비기한을 `NULL`로 전환한다.
9. `폐기 없음`은 폐기 이력을 저장하지 않는다.
10. `폐기 완료`는 저장 직후, `폐기 없음`은 팝업에서 `나중에 확인`을 선택한 경우 `미확인` 흐름으로 이동한다.
11. `폐기 없음`에서 입력을 강제하지 않아도 되는 이유는 상품이 삭제되지 않고, `NULL` 상태도 이후 다시 확인할 `미확인` 상태로 남기 때문이다.
12. 저장 후 별도 완료 메시지는 필수로 두지 않는다.
13. `소비기한 수정`은 메인 카드에 직접 강하게 노출하지 않는다.
14. 이유는 사용자가 핵심 처리 흐름 대신 소비기한만 수정하고 끝내면 실제 처리 의미가 남지 않을 수 있기 때문이다.
15. 따라서 수정 계열 액션은 `더 보기` 안에 묶어 메인 처리 흐름과 시각적으로 분리한다.

### 좌측 사이드바: 미확인 대상

좌측 사이드바는 `expiration_date = NULL`인 활성 상품을 보여준다.

표기:

- 사용자 용어는 `미확인`으로 통일한다.

역할:

- 다음 소비기한을 아직 확인하지 못한 상품을 한 번에 모아둔다.
- 메인 처리 대상과 섞지 않고, 별도 스크롤 패널로 본다.

가능한 행동:

- 소비기한 입력
- 아카이브 전환

## 3. 아카이브 조회 페이지

아카이브 상품은 별도 조회 페이지에서 관리한다.

1차 범위:

- 아카이브 상품 목록 조회
- 검색
- 복구 버튼

복구 규칙:

- 복구 시 상품 상태는 `active`가 된다.
- 복구 시 현재 소비기한은 `NULL`로 둔다.
- 복구 직후 상품은 메인 처리 대상이 아니라 `미확인` 사이드바 대상이 된다.

## 4. 날짜 입력 규칙

1. 현재 구현은 브라우저 기본 `input type="date"`를 사용한다.
2. 기준 날짜와 소비기한 입력 모두 직접 수정 가능해야 한다.
3. 클릭 타깃이 좁아 불편하지 않도록 입력 래퍼 전체와 보조 버튼에서 date picker를 열 수 있게 둔다.
4. 이후 실제 운영에서 숫자 직접 입력 UX가 더 낫다고 판단되면 그때 별도 입력 방식으로 다시 검토한다.

## 5. 1차에서 제외할 것

다음 항목은 Vue 1차 범위에서 제외한다.

1. 검색 없는 메인 화면의 추가 필터 확장
2. 판매/매출 분석 화면
3. 사용자 권한 관리
4. 여러 점포 지원
5. 변경 이력 추적 화면
6. `유제품 / 미선택` 외의 카테고리 확장

## 6. 구현 우선순위

1. 상품 등록
2. 바코드 기반 등록 팝업
3. 메인 처리 대상 조회와 `오늘 처리 / 전체` 필터
4. 미확인 사이드바
5. 폐기 처리 후 상태 반영
6. 상품명 수정
7. 아카이브 전환
8. 아카이브 목록 조회와 복구

## 7. 프론트에서 꼭 검증할 질문

Vue 1차 구현에서 반드시 확인해야 할 것은 아래와 같다.

1. 상품 등록 후 `시스템에 계속 남는 느낌`이 충분히 드는가
2. `오늘 처리`가 기본 진입 필터로서 실제 업무 흐름에 잘 맞는가
3. `미확인` 상품을 사이드바로 분리했을 때 메인 흐름이 더 편해지는가
4. 폐기 후 다음 상태 반영이 메시지 없이도 혼란 없이 이해되는가

## 8. 현재 프론트 구현 위치

- Vue 앱 루트는 `frontend/` 디렉터리다.
- 기본 실행은 `npm install` 후 `npm run dev`다.
- 백엔드 API 주소는 `VITE_API_BASE_URL`로 명시한다.
- 로컬 개발과 production 빌드 기준은 모두 `/api`다.
- 로컬 개발에서는 Vite dev server가 `/api` prefix를 제거해 `http://localhost:8000` 백엔드로 프록시한다.
- 현재 MVP는 Vue Router를 사용하지 않고 공식 화면 URL을 `/` 하나로 둔다.
- fallback으로 열린 정의되지 않은 프론트 경로는 앱 부팅 시 `/`로 정규화한다.
- SPA fallback과 routing 정책은 `docs/issue-28-spa-fallback-routing-policy.md`를 기준으로 둔다.
- production의 실제 `/api` reverse proxy 구현과 검증은 배포 구조가 확정된 뒤 별도 이슈에서 확인한다.
