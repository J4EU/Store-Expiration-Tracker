# Data EBS 백업·복구 전략

이 문서는 Data EBS의 SQLite 데이터를 무엇으로 백업하고, 장애가 나면 어떤 규칙으로 복구하는지 기록한다. 결정 과정과 근거는 [Issue #98](https://github.com/J4EU/Store-Expiration-Tracker/issues/98)의 코멘트에 있다. 복원 명령은 [Data EBS 스냅샷 복원](operations/data-ebs-snapshot-restore.md)을 따른다.

## 범위

대상은 Data EBS에 있는 SQLite DB다. 백업 수단은 EBS 스냅샷이고, 실수로 지운 스냅샷은 Recycle Bin으로 되살린다.

이 문서에서 다루지 않는 것은 아래 이슈에서 다룬다.

- AWS 밖 사본: [Issue #113](https://github.com/J4EU/Store-Expiration-Tracker/issues/113)
- 매일 무결성 검사: [Issue #112](https://github.com/J4EU/Store-Expiration-Tracker/issues/112)
- 스냅샷 이상 감지: [Issue #114](https://github.com/J4EU/Store-Expiration-Tracker/issues/114)
- 자격 증명 유출 시 스냅샷 삭제 방지: [Issue #125](https://github.com/J4EU/Store-Expiration-Tracker/issues/125)
- EC2 start/stop 자동화: [Issue #111](https://github.com/J4EU/Store-Expiration-Tracker/issues/111)

Root EBS에 쌓인 데이터는 Data EBS 스냅샷에 담기지 않는다. Data EBS가 mount되지 않은 채 앱이 뜨는 문제는 [Issue #110](https://github.com/J4EU/Store-Expiration-Tracker/issues/110)에서 다룬다.

## 지키려는 데이터

| 데이터 | 잃었을 때 | 우선순위 |
| --- | --- | --- |
| 상품 목록 | 하나씩 수동으로 등록해 쌓은 데이터다. 통째로 잃으면 다시 등록하는 데 몇 주가 걸릴 수 있다. | 가장 높음 |
| 소비기한 정보 | 운영자 혼자 다시 검사해도 일주일 안에 회복할 수 있다. | 중간 |
| 폐기 이력 | 점포 시스템 `수불 - 통합폐기조회`에서 날짜를 지정해 다시 조회할 수 있다. | 낮음 |
| 관리자 계정 | 앱이 시작할 때 `ADMIN_PASSWORD` 환경 변수로 다시 만든다. | 낮음 |

## RPO

RPO는 최대 한 회차(그날 입력분)다.

- 쓰기는 소비기한 업무 시간에만 일어난다. 그래서 스냅샷을 자주 찍는 것보다, 그날 마지막 쓰기 이후에 찍는 것이 중요하다.
- 그날 입력분을 잃어도 진열대 확인과 바코드 재입력으로 다시 채울 수 있고, 폐기 이력은 점포 시스템에서 다시 조회할 수 있다.
- EBS 고장으로 당일 데이터를 잃을 확률은 연간 약 0.06%(gp3 연간 고장률 0.2% × 스냅샷 전 위험한 시간 약 7시간/24시간)다.

전제는 운영자가 매일 출근해 다음 날 진열대를 다시 확인할 수 있다는 것이다.

## 스냅샷 구성

구성은 [infra/data-ebs/snapshot.tf](../infra/data-ebs/snapshot.tf)에 있다.

| 항목 | 값 |
| --- | --- |
| 생성 방식 | Data Lifecycle Manager(DLM) 정책 하나 |
| 대상 | `Backup` 태그가 붙은 볼륨 |
| 일간 스냅샷 | 매일 03:00(KST) 시작, 30일 보관 |
| 월간 스냅샷 | 매월 1일 03:00(KST) 시작(전월 말일 업무분까지 담음), 12개월 보관 |
| 삭제 방지 | `Backup` 태그가 붙은 스냅샷을 지우면 Recycle Bin에 28일 보존 |

### 시점

- DLM은 지정 시각부터 1시간 안에 시작한다. 03:00은 03:00~04:00에 시작하므로, 한국 날짜로는 항상 업무일 다음 날이다.
- EC2를 켜지 않은 날에도 똑같이 찍는다. 복원 지점은 업무 회차보다 일수로 따지는 것이 일관적이다.
- 월간 스냅샷은 그달의 마지막 상태를 남긴다. DLM은 시간대를 지정할 수 없어, UTC 기준 매월 말일 18:00(`L`)으로 KST 1일 03:00을 맞춘다. 비활성 테스트 정책으로 DLM이 `L`을 받아 주는 것을 확인했다.

### stop 상태 전제

스냅샷은 EC2가 stop된 상태에서 찍혀야 한다. 실행 중에 찍으면 crash-consistent일 뿐이라, 복원 후 DB가 정상인지 따로 확인해야 한다.

- DLM은 EC2가 stop됐는지 보장하지 않는다. 지금은 업무가 끝나면 수동으로 stop하고, 자동 stop은 #111에서 다룬다.
- 복구 중이라도 03:00 전에는 EC2를 stop한다. 아래 복구 규칙을 따른다.

### 보관 기간

- 일간 30일: 사고를 바로 알았을 때 볼륨을 통째로 되돌리는 용도다.
- 월간 12개월: 상품 목록이 조용히 망가진 것을 몇 달 뒤에 발견했을 때 쓰는 용도다. 점검은 상품이 진열된 라인 단위로 하므로, 소비기한이 먼 상품도 넉넉하게 6~8개월 안에 다시 확인된다. 12개월은 여기에 여유를 더한 값이다.
- 12개월이 지나 지워지는 것은 데이터가 아니라 그 시점으로 돌아갈 수 있는 복원 지점이다.
- Recycle Bin 28일: 스냅샷이 지워진 것을 알아차리는 데 3주면 된다고 보고 여유를 더했다.

### `Backup` 태그 주의

- `Backup` 태그가 없는 볼륨은 DLM이 찍지 않는다. 복원하며 새 볼륨을 만들면 반드시 태그를 붙인다.
- `Backup` 태그가 없는 스냅샷은 Recycle Bin 규칙에 해당하지 않아, 지우면 바로 사라진다. 보호가 필요한 수동 스냅샷에는 태그를 붙인다.

## 복구 규칙

복구 목표 지표는 RPO만 둔다. RTO는 두지 않고, 아래 시각 기준 규칙을 따른다.

| 시각 | 하는 일 |
| --- | --- |
| 20:30 | 보통 EC2를 start할 때 장애를 알아차리고 복구를 시작한다. |
| 21:30 | 복구를 멈추고 대체 조회로 그날 소비기한을 확인한다. |
| 21:30~23:30 | 소비기한 관리, 냉장 물류 정리, 식사, 뒷정리를 하고 23:30에 퇴근한다. 복구하지 않는다. |
| 00:00 | 집에서 복구를 재개한다. |
| 03:00 | 복구를 끝내고 EC2를 stop한다. 끝내지 못해도 멈추고 EC2를 stop한다. 남은 복구는 다음 날 출근 준비(16:00) 전을 목표로 한다. |

### 대체 조회

- 폐기 처리(재고 감소)는 POS로 할 수 있지만, "오늘 소비기한이 끝나는 상품" 확인은 이 서비스에만 의존한다. 그래서 복구가 늦어지면 대체 조회가 필요하다.
- 대체 수단은 #113의 로컬 사본을 읽기 전용으로 조회하는 쿼리다. 쿼리는 화면의 "오늘 처리" 규칙(지난 상품, 오늘, 내일 유제품)을 옮긴 것이다.
- 21:30으로 정한 것은 업무 흐름이 끊기지 않게 하기 위해서다. 22:30 마감 전에 그날 소비기한 확인을 끝내야 하고, 21:40~22:10에 냉장 물류가 들어온다.
- 라인을 직접 확인하는 방법은 최소 2시간, 실제로는 3~4시간 이상 걸려 대체 수단에서 제외했다.

### RTO를 두지 않는 이유

- 하루 약 2시간 쓰는 서비스라, 사용 시간 밖에서 멈추는 것은 비용이 없다.
- 20:30 기동 때 장애를 100% 알아차리기는 어렵다. "알아차린 뒤 몇 시간"으로 정한 목표는 알아차리는 시점에 따라 의미가 흔들린다.
- 실제로 행동을 정하는 것은 21:30이라는 고정 시각이다.

### 복구의 전제

- 기동 시점에 이상을 알아차릴 수 있어야 한다(#110, #114).
- 복원 테스트에서 잰 볼륨 교체 소요 시간은 약 7분 35초다. 명령과 판단 기준을 미리 준비한 상태에서 잰 값이라, 실제 사고 때는 원인 파악과 판단에 시간이 더 걸릴 수 있다.

## 복원 방법

명령은 [Data EBS 스냅샷 복원](operations/data-ebs-snapshot-restore.md)에 있다. 이 문서는 어떤 경우에 어떤 방법을 쓰는지만 적는다.

| 경우 | 방법 |
| --- | --- |
| 볼륨 전체를 특정 시점으로 되돌린다 | 스냅샷으로 새 볼륨을 만들어 기존 볼륨과 교체한다. 기존 볼륨은 바로 지우지 않는다. |
| 일부 데이터만 되돌린다 | 그 시점 스냅샷으로 임시 볼륨을 만들고, 그 안의 SQLite DB에서 필요한 데이터를 추출해 현재 DB에 수작업으로 반영한다. |
| 스냅샷을 실수로 지웠다 | Recycle Bin에서 되살린다. 되살린 스냅샷도 DLM이 계속 관리한다. |

복원한 DB는 `PRAGMA integrity_check`로 정상인지 확인한다.

## 한계와 남는 위험

- 마지막 스냅샷 이후의 데이터는 잃는다.
- 복원 단위가 볼륨 전체라, 일부 데이터만 되돌리려면 수작업이 필요하다.
- 복원하면 볼륨 ID가 바뀌어 `infra/data-ebs` state를 새 볼륨으로 맞춰야 한다.
- 보관 기간보다 늦게 발견한 손상은 복구할 수 없다.
- 스냅샷이 같은 계정·리전에만 있어, 계정이 정지되거나 해지되면 볼륨과 함께 사라진다. AWS 밖 사본(#113)으로 대비한다.
- 자격 증명을 가진 침입자가 Recycle Bin 규칙까지 끄고 스냅샷을 지우는 경우는 막지 못한다(#125).
- #113이 끝나기 전에는 대체 수단이 없어, 22:30 마감 전에 그날 소비기한을 확인하지 못할 수 있다. 그래서 #113은 실데이터 마이그레이션(실제 운영 시작) 전에 끝낸다.

## 재검토 조건

- EC2 start 시각이나 근무 시간대가 바뀔 때
- 근무 일정이 바뀌어 다음 날 바로 진열대를 다시 확인할 수 없게 될 때
- 폐기 이력 조회 기능이 생기거나, 점포 시스템으로 되살릴 수 없고 이 DB에만 있는 데이터가 늘어날 때
