# MVP

## 문서 목적

이 문서는 `Store-Expiration-Tracker`의 MVP 범위와 구현 원칙을 정의한다.

기술 스택이나 상세 화면 설계보다, 제품이 우선 해결할 문제와 포함 범위를 명확히 하는 데 목적이 있다.

## 1. 해결하려는 문제

이 프로젝트가 우선 해결하려는 문제는 다음과 같다.

> 한 번 관리하기 시작한 상품이, 다음 소비기한이 비어 있더라도 시스템에서 사라지지 않고 계속 추적되어야 한다.

이 프로젝트의 목표는 전체 재고 관리 시스템을 만드는 것이 아니라, **상품별 소비기한 관리 상태를 지속적으로 유지하는 도구**를 만드는 것이다.

## 2. MVP에서 꼭 포함할 범위

MVP는 다음 기능을 우선 범위로 둔다.

1. 상품을 등록할 수 있다.
2. 상품별로 현재 추적 중인 소비기한 1개를 저장할 수 있다.
3. 다음 소비기한을 아직 확인하지 못한 경우, `소비기한 비어 있음` 상태로 상품을 남겨둘 수 있다.
4. 오늘 확인하거나 처리해야 할 상품 목록을 볼 수 있다.
5. 폐기 또는 확인 이후, 같은 상품의 다음 상태로 갱신할 수 있다.
6. 상품이 추적 대상에서 완전히 사라지지 않도록 상태를 유지할 수 있다.

## 3. MVP에서 제외할 범위

다음 항목은 MVP 범위에서 제외한다.

1. 편의점 전체 재고 관리
2. 발주 기능
3. 판매 분석
4. 매출 관리
5. 여러 점포 지원
6. 사용자 권한 관리
7. 바코드 스캐너 연동 고도화
8. 자동 알림, 문자, 푸시 발송
9. 복잡한 분석 대시보드

## 4. 핵심 사용자

MVP의 1차 사용자는 다음과 같이 정의한다.

- 편의점에서 직접 소비기한 등록과 폐기 업무를 수행하는 근무자
- 상품별로 가장 임박한 소비기한 하나를 기준으로 관리하는 사람
- 빠르게 조회하고, 바로 상태를 갱신해야 하는 사람

## 5. 핵심 데이터 모델

MVP의 핵심은 상품별 현재 소비기한 추적이므로, 데이터 모델은 다음 세 영역을 중심으로 구성한다.

### 상품

- 상품 ID
- 상품명
- 바코드
- 상품 상태
- 아카이빙 일시

상품 등록 및 조회의 기준은 `바코드`이다.  
DB 내부에서는 각 상품 row에 `Primary Key ID`를 두고, 상태 테이블과 이력 테이블이 이 값을 참조한다.

### 상품별 현재 소비기한 상태

- 상태 ID
- 상품 ID
- 현재 추적 중인 소비기한 날짜
- 마지막 갱신 일시

각 상품은 현재 소비기한 상태 row를 하나만 가진다.  
소비기한이 바뀌면 새 row를 추가하지 않고, 기존 row를 수정한다.
`expiration_date`가 있으면 현재 추적 중인 소비기한이 있는 상태이고, `NULL`이면 다음 소비기한이 아직 없거나 확인되지 않은 상태다.

### 폐기 이력

- 폐기 이력 ID
- 상품 ID
- 폐기 처리 일자
- 폐기 수량

### 아카이빙 정책

상품은 DB에서 삭제하지 않는다.

- 현재 계속 관리 중인 상품은 `active`
- 더 이상 발주하지 않거나 추적하지 않는 상품은 `archived`

`archived` 상태의 상품은 기본 조회 목록에서는 제외하지만, 과거 폐기 이력과 운영 기록 분석에는 계속 활용한다.

아카이빙 여부는 시스템이 자동으로 결정하지 않으며, 사용자가 직접 전환한다.

상태는 다음 두 층으로 구분한다.

- 상품 레벨 상태: `active`, `archived`
- 현재 소비기한 보유 여부: `expiration_date`의 `값 있음`, `NULL`

## 6. 핵심 사용자 흐름

### 흐름 1. 상품 등록

1. 사용자가 상품을 선택하거나 등록한다.
2. 가장 임박한 소비기한을 입력한다.
3. 시스템은 해당 상품의 현재 소비기한을 저장한다.

### 흐름 2. 폐기 처리 및 다음 소비기한 반영

1. 사용자가 오늘 처리할 상품 목록에서 상품을 확인한다.
2. 기존 상품을 폐기 처리하고, 폐기 수량을 기록한다.
3. 진열대에 남아 있는 다음 상품의 소비기한을 확인한다.
4. 새 소비기한이 있으면 기존 row의 날짜를 갱신하고, 없으면 `expiration_date`를 `NULL`로 바꾼다.

### 흐름 3. 소비기한 미확인 상태 유지

1. 사용자가 기존 상품을 처리한다.
2. 다음 상품의 소비기한을 바로 확인할 수 없거나, 아직 등록할 값이 없습니다.
3. 시스템은 상품을 삭제하지 않고 `expiration_date = NULL` 상태로 유지한다.
4. 사용자는 이후 다시 확인해야 할 대상임을 목록에서 볼 수 있다.

### 흐름 4. 오늘 확인할 대상 조회

1. 사용자가 앱에 들어옵니다.
2. 시스템은 `소비기한이 내일까지인 상품`과 `현재 소비기한이 비어 있는 상품`을 서로 다른 섹션으로 나누어 보여줍니다.
3. 사용자는 목록에서 바로 다음 작업을 선택한다.

### 흐름 5. 상품 아카이빙

1. 사용자가 더 이상 현재 추적하지 않을 상품을 직접 선택한다.
2. 시스템은 해당 상품을 삭제하지 않고 `archived` 상태로 전환한다.
3. 아카이빙된 상품은 기본 추적 목록에서는 보이지 않습니다.
4. 기존 폐기 이력과 운영 데이터는 그대로 유지됩니다.
5. 필요하면 사용자가 다시 `active` 상태로 되돌릴 수 있다.

## 7. MVP에서 필요한 화면 또는 기능 단위

구현 방식과 관계없이, MVP에는 다음 기능 단위가 필요하다.

1. 메인 대시보드
2. 상품 등록 및 예외 수정 기능
3. 소비기한 수정 기능
4. `소비기한 비어 있음` 처리 기능
5. 상품 아카이빙 기능

메인 대시보드는 MVP의 중심 화면이다.  
`소비기한이 내일까지인 상품`과 `현재 소비기한이 비어 있는 상품`을 한 화면 안에서 구분해 보여주고, 사용자가 바로 상태를 갱신할 수 있어야 한다.

초기 버전에서는 여러 화면을 오가는 구조보다, 메인 대시보드에서 조회와 상태 변경이 최대한 이어지는 구성을 우선한다.

다만 이후에는 아카이빙된 상품 조회, 이력 조회, 보조 관리 기능이 추가될 수 있으므로, 네비게이션 구조로 확장 가능한 형태를 염두에 둔다.

## 8. 우선순위

가장 먼저 검증해야 하는 것은 UI의 완성도보다 다음 운영 규칙이다.

> 소비기한 값이 없어도, 한 번 관리하기 시작한 상품은 시스템에서 사라지지 않는다.

이 규칙이 지켜져야 이후 정렬, 검색, 입력 방식, 화면 구성 개선이 의미를 갖는다.

같은 이유로 폐기 기록은 집계 가능한 형태로 누적되어야 하며, 상품 삭제로 인해 분석 데이터가 끊기지 않아야 한다.

## 9. 구현 기준

다음 항목은 구현 시 고정 원칙으로 사용한다.

1. 사용자는 상품을 `바코드`를 기준으로 등록하고 조회한다. MVP는 수기 입력으로 시작하되, 이후 바코드 스캐너 입력으로 확장할 수 있는 구조를 유지한다.
2. `expiration_date`가 `NULL`인 상품은 다음 소비기한이 확인되어 갱신되기 전까지 목록에 유지한다.
3. 메인 화면에서는 `소비기한이 내일까지인 상품`과 `현재 소비기한이 비어 있는 상품`을 서로 다른 섹션으로 분리해 보여줍니다.
4. 폐기 처리는 현재 상태 갱신과 별개로 이력 테이블에 누적 저장한다.
5. 폐기 이력은 `언제`, `어떤 상품이`, `몇 개` 폐기되었는지를 남기는 데 집중한다.
6. 각 상품은 현재 소비기한 상태 row를 하나만 가지며, 변경 시 기존 row를 수정한다.
7. 상품은 삭제하지 않고 `active` 또는 `archived` 상태로 관리한다.
8. 아카이빙은 자동 조건이 아니라 사용자가 수동으로 결정하며, 필요 시 다시 활성화할 수 있다.
9. `archived` 상품은 기본 운영 화면에서 제외하지만 분석 대상에서는 유지한다.
10. MVP에는 분석 기능 화면을 포함하지 않지만, 폐기 데이터 기반 발주 판단을 위해 집계 가능한 DB 구조를 설계한다.
11. DB 내부에서는 `상품 ID`를 `Primary Key`로 사용하고, 상태 및 이력 테이블은 이 값을 참조한다.

## 10. 다음 단계

구현은 다음 순서로 진행한다.

1. 현재 소비기한 표현 방식과 데이터 구조 확정
2. 핵심 흐름별 입력/출력 정의
3. 메인 대시보드 섹션 구성 정의
4. 간단한 화면 스케치 또는 CLI 시나리오 작성
5. 기술 스택 선택
6. 첫 프로토타입 구현

## 11. 데이터 확장 방향

이 프로젝트는 운영 보조 도구로 시작하되, 이후 폐기 데이터를 기반으로 발주 판단을 보조할 수 있는 구조를 지향한다.

향후 고려하는 활용 예시는 다음과 같다.

1. 최근 3개월 기준 상품별 폐기 수량 집계
2. 특정 기간 동안 자주 또는 많이 폐기된 상품 식별
3. 폐기 데이터를 바탕으로 발주 유지 여부 검토
4. 아카이빙된 상품과 폐기 이력의 관계 확인

이 확장 방향을 고려해, MVP 단계에서도 다음 원칙을 유지한다.

1. 상품 마스터는 삭제하지 않는다.
2. 폐기 이벤트는 수량을 포함해 누적 기록한다.
3. 현재 상태 테이블과 이력 테이블을 분리한다.
4. 운영 화면 기준 데이터와 분석 기준 데이터를 분리해서 생각한다.
