# Technology Stack

## 현재 결정

- Backend: FastAPI
- Frontend: Vue

이 조합은 현장 소비기한 관리 흐름을 구현한 애플리케이션을 만들고, 이를 배포·운영 경험으로 연결한다는 현재 프로젝트 목적에 맞춰 선택했다.

## 선택 이유

- FastAPI는 상태 전이 중심의 API를 비교적 가볍게 구성하기에 적합하다.
- Python 기반 Backend는 이후 폐기 데이터 집계와 분석 방향을 검토할 때 자연스럽게 이어질 수 있다.
- Vue는 메인 운영 화면을 구현하는 데 필요한 복잡도를 과도하게 키우지 않는다.
- Frontend 정적 파일, API 서버, SQLite, reverse proxy를 분리해 배포·운영 경계를 다룰 수 있다.

## 검토한 대안

- Spring Boot + React는 현재 프로젝트 규모에 비해 구현·학습 비용이 컸고, 당시 우선순위였던 배포·운영 경험 확보와 맞지 않아 보류했다.
- Django + Vue는 인증, ORM, admin 기능에 강점이 있지만, 현재 제품은 관리형 backoffice보다 한 화면에서 빠르게 상태를 전이하는 흐름이 중심이라 그 강점을 충분히 활용하기 어려웠다.
- Node.js + Vue는 기존 배포 경험을 활용할 수 있었지만, 향후 폐기 데이터 분석 가능성과 Python 생태계 연결을 고려해 FastAPI를 선택했다.

## 수용한 trade-off

- 이 선택은 대규모 사용자·복잡한 권한 체계·관리자 백오피스를 전제로 최적화한 선택은 아니다.
- 프레임워크를 깊게 학습하는 것보다 현재 운영 문제와 인프라 운영 경험을 우선한다.
- 현재 기술 스택 자체가 API 계약, DB 구조, 배포 검증의 source of truth는 아니다. 실제 구현은 코드와 관련 설정을 따른다.

## 재검토 조건

아래 요구가 실제로 생기면 스택 또는 구조를 다시 검토한다.

- 여러 운영자와 세분화된 권한을 관리해야 할 때
- 여러 점포 또는 외부 시스템 연동으로 도메인·운영 복잡도가 크게 늘어날 때
- 현재 Vue 화면 구조로 유지하기 어려운 화면 전환·공유 URL·route guard 요구가 생길 때
- 운영 데이터 규모나 분석 요구가 현재 SQLite·애플리케이션 구조의 경계를 넘을 때

이 조건은 즉시 교체 계획이 아니라, 현재 선택이 더 이상 맞는지 판단할 신호다.
