# Issue 작성

Issue의 목표는 근거 없는 내용을 지어내지 않는 것이다.
근거로 쓸 수 있는 범위는 유형마다 다르며, 2번에 적혀 있다.

## 1. 유형 확인

- 유형은 구현, backlog 두 가지다.
- backlog 이슈는 문제, 개선 아이디어, 잠재적 위험처럼 필요성은 인지했지만 아직 구체적인 작업으로 확정하지 않은 사항을 보관한다. 조사나 구체화를 끝내야 할 의무는 없고, 구현으로 이어질 필요도 없다. 필요할 때 검토해 결론을 내린다.
- 구현 이슈는 `.github/ISSUE_TEMPLATE/implementation.md`를 쓴다. backlog 이슈는 템플릿 파일 없이 아래 규칙을 따른다.
- 유형은 사용자가 정한다. 사용자가 말하지 않았으면 판단하지 말고 묻는다.

## 2. 내용 정리

구현 이슈
- 근거는 사용자의 말뿐이다. 사용자가 말한 내용을 템플릿 각 섹션에 옮긴다. 표현은 다듬어도 되지만 내용을 더하지 않는다.
- 섹션 구조와 작성 방법은 템플릿과 그 주석을 따른다. 템플릿에 없는 섹션은 추가하지 않는다.
- 사용자의 말로 채울 수 없는 섹션은 지어내지 말고 사용자에게 묻는다.
- `관련 링크 / 참고`에는 사용자가 알려준 것과 repo에서 실제로 확인한 것만 넣는다. 없으면 비워둔다.

backlog 이슈
- 근거는 사용자의 말, 이 대화에서 사용자와 나눈 내용, repo에서 실제로 확인한 것이다.
- 대화에서 흩어진 내용을 정리해서 쓰되, 대화에 없던 새 주장은 더하지 않는다.
- 무엇이 보였는지, 왜 신경 쓰이는지를 근거로 채울 수 없으면 지어내지 말고 사용자에게 묻는다.

## 3. 유형별 규칙

구현 이슈
- `이번에 할 것`에 구현 방법(라이브러리, 구조, 설계)은 사용자가 말한 경우에만 적는다.
- `완료 조건`은 구현 방식이 아니라 어떻게 동작하면 끝나는지로 적는다.

backlog 이슈
- 본문은 `## 설명` 한 섹션만 쓴다.
- 구현 이슈만큼 상세하게 쓰지 않는다. 다만 맥락을 모르는 사람이 이것만 읽어도 무엇이 보였는지 이해될 만큼은 쓴다.
- 사용자가 말한 아이디어는 적되, 해결책이나 구현 방향을 덧붙이지 않는다.

## 4. 제목

- 제목은 자연스러운 한국어 문장으로 쓴다. `feat:` 같은 type prefix를 붙이지 않는다.
- backlog 이슈 제목은 인지한 문제·필요·의문을 그대로 쓴다. "왜 ~하지?" 같은 의문형은 의문일 때만 쓴다. 사용자가 말하지 않은 해결 방법은 제목에 넣지 않는다.

## 5. 초안 확인과 생성

- 유형, 제목, 본문 초안을 사용자에게 보여주고, 승인 전에는 Issue를 생성하지 않는다.
- 사용자가 수정을 요청하면 반영한 초안을 다시 보여주고 승인을 받는다.
- 승인 후 `gh issue create --title "<제목>" --body-file <파일>`로 생성한다. backlog 이슈는 `--label backlog`를 붙인다.

## 6. backlog 이슈 정리 코멘트

backlog 이슈를 검토해서 결론을 남길 때 정리 코멘트를 쓰고, 이슈를 닫는다. 작업이 필요하면 backlog 이슈를 이어서 쓰지 않고 후속 구현 이슈를 만든다.

- 근거는 backlog 이슈와 같다. 사용자가 정한 것과 정하지 않은 것을 구분하고, 정하지 않은 것을 결론처럼 쓰지 않는다.
- `## 최종 정리` 아래에 결론은 꼭 쓴다. 후속 이슈가 있으면 체크리스트로 쓰고, 이슈가 생성된 항목만 체크한다. 근거, 남은 위험, 미정 같은 섹션은 필요할 때만 쓴다.
- 초안을 사용자에게 보여주고, 승인 후 `gh issue comment <번호> --body-file <파일>`로 남긴다. 이슈를 닫는 것도 사용자 승인 후에 한다.
