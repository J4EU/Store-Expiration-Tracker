# PR 작성

PR 본문은 사용자가 직접 쓰지 않는다. 목표는 확인된 사실만으로 본문을 채우는 것이다.
본문 구조는 `.github/pull_request_template.md`를 그대로 따르고, 각 섹션의 작성 방법은 템플릿 주석을 따른다.

## 1. 사실 수집

본문의 근거는 아래 네 가지뿐이다. 여기에 없는 내용은 쓰지 않는다.

- base 브랜치 대비 diff와 커밋 목록 (`git diff <base>...HEAD`, `git log <base>..HEAD`)
- 연결된 Issue 본문 (`gh issue view <번호>`)
- 이번 세션에서 직접 실행한 검증 결과
- 사용자가 대화에서 알려준 내용

연결된 Issue 번호를 대화에서 확인할 수 없으면 추측하지 말고 사용자에게 묻는다.

## 2. Issue 연결 판단

- Issue 완료 조건의 체크박스를 하나씩 diff와 검증 결과에 대조한다.
- 모든 항목에 근거가 있을 때만 `Closes #번호`를 쓴다. 하나라도 애매하면 `Related to #번호`를 쓴다.
- 조사 이슈(`research.md` 기반)는 `Closes`로 연결하지 않는다. 결정은 사용자가 내리기 때문이다.

## 3. 제목과 본문 작성

- 제목은 CLAUDE.md의 Commit 메시지 형식을 따른다.
- 검증 섹션에는 직접 실행한 것만 "수행함"으로 쓴다. 사용자의 수동 확인은 사용자가 대화에서 말한 경우에만 쓴다.
- 변경 이유가 Issue나 대화에 없으면 만들어내지 않는다.

## 4. 자가 점검

초안의 문장마다 근거가 1번 안에 있는지 확인하고, 근거가 없는 문장은 지운다.

## 5. 초안 확인과 생성

- 제목과 본문 초안을 사용자에게 보여주고, 승인 전에는 PR을 생성하지 않는다.
- 작업 중 발견한 개선 사항이나 후속 작업 후보는 PR 본문에 넣지 않고, 초안과 별도로 사용자에게 알린다.
- 승인 후 `gh pr create --title "<제목>" --body-file <파일>`로 생성한다. 브랜치가 원격에 없으면 push도 이 승인 범위에 포함해 함께 진행한다.
- 사용자가 수정을 요청하면 반영한 초안을 다시 보여주고 승인을 받는다.
